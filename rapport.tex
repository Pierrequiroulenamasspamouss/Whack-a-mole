\section{Introduction}
This project was carried out as part of the Digital Electronics course (ELEN0040). The objective is to design and implement a classic "Whack-a-mole" game on a CPLD (Complex Programmable Logic Device).

The game consists of hitting "moles" represented by LEDs that light up randomly on a grid. The player must press the button corresponding to the lit LED to score points within a limited time. This implementation utilizes fundamental digital logic concepts such as Finite State Machines (FSM), clock synchronization, and pseudo-random number generation via a Linear Feedback Shift Register (LFSR).

The user interface consists of:

This could be considered "cheating", however if we wanted to have a pretty interface to the game, this approach was both the easiest to implement, and the most expandable (for example counting up to 99999 score can be achieved very easily)

\section{Logic Architecture}

\subsection{Code Structure}
The logic of the \texttt{Whackamole} entity is designed around an architecture consisting of four independent VHDL processes interconnected by trigger signals:
\begin{itemize}
    \item \textbf{lfsr\_proc}: Continuously generates pseudo-random sequences.
    \item \textbf{timer\_proc}: Generates the \texttt{global\_tick} prescaler and handles output pulse timers.
    \item \textbf{game\_fsm\_proc}: Manages the global state of the game (WAIT\_START, PLAYING) and the overall countdown timer.
    \item \textbf{moles\_fsm\_proc}: Analyzes button inputs, triggers score events, and controls the lifespans of the 9 independent moles dynamically.
\end{itemize}
This  approach is in every way superior to our first idea, which was similar to a CPU, waiting for clock cycles to trigger events. 

\subsection{Finite State Machine (FSM)}
The core control logic of the game is handled by the \texttt{game\_fsm\_proc} process through a finite state machine with two primary states:
\begin{itemize}
    \item \textbf{WAIT\_START (IDLE)}: The default state upon power-up and game over. In this state, all LEDs blink synchronously with the \texttt{slowclock} to attract attention and indicate readiness. The system transitions to \texttt{PLAYING} when the \texttt{startButton} is pressed.
    \item \textbf{PLAYING}: The active game state lasting 30 timer ticks. When the \texttt{game\_duration\_timer} reaches zero, the system instantly returns to \texttt{WAIT\_START}.
\end{itemize}

The initialization and transition of these states are managed within the main FSM process:
\begin{lstlisting}[language=VHDL]
type game_state_type is (WAIT_START, PLAYING);
signal game_state : game_state_type := WAIT_START;
-- ... inside game_fsm_proc
case game_state is
    when WAIT_START =>
        score_reset <= '0';
        game_duration_timer <= 30; -- Reset du timer principal
        if startButton = '1' and startButton_prev = '0' then
            game_state <= PLAYING;
            score_reset <= '1'; -- Pulse reset vers l'ecran
        end if;

    when PLAYING =>
        score_reset <= '0';
        
        -- Gestion du Timer de jeu total et penalites
        if (slowclock = '1' and slowclock_prev = '0') or trigger_miss = '1' then
            if game_duration_timer > 0 then
                game_duration_timer <= game_duration_timer - 1;
            end if;
        end if;

        -- Transition a la fin du temps
        if game_duration_timer = 0 then
            game_state <= WAIT_START;
        end if;
end case;
\end{lstlisting}

\emph{Note:} We have seen that the code we created does not in fact produce a FSM when analyzing the output of the RTL view. Since we only use two states, it seems Quartus optimized the code to not use a FSM inside the hardware logic implementation, and rather use a succession of logic gates, and did not compress parts of it into state machines. We at first failed to understand why our state-machine implementation did not result into a state machine logic implementation, before realizing that the code written and the hardware implementation can be drastically different, but output the same result. 

\subsection{Pseudo-Random Generation (LFSR)}
To ensure the unpredictability of mole appearances, we searched the Internet to find a suitable random number generation method, and instead of picking up the output of an unpredictable entry (ex : floating input gate or 555 timer running a 4 bit shift register very fast), we found that we could implement an LFSR, Linear-Feedback shift register. Thus we implemented a 5-bit LFSR is implemented. This component generates a sequence of numbers that appears random despite being deterministic. The polynomial used is $x^5 + x^3 + 1$. 
\begin{lstlisting}[language=VHDL]
-- LFSR update code snippet
lfsr <= lfsr(3 downto 0) & (lfsr(4) xor lfsr(2));
\end{lstlisting}
At each \texttt{fastclock} cycle, the register evolves. When the system decides to spawn a new mole, the current value of the LFSR (truncated to 4 bits) is converted to an index between 0 and 8, used to light up one of the nine output LEDs. The sequence begins with [1 0 0 0 0] to ensure that the pattern does not start repeating itself (ex : [ 0 0 0 0 0 ] would repeat zeros indefinitely, we tried. Since we do not know when the user will start the game, when the user is waiting in the WAIT\_START state, the fastclock has plenty of time to run and "randomize" this LFSR. 

\subsection{Time Management and Synchronization}
The system uses two clocks passed through the ports:
\begin{itemize}
    \item \texttt{fastclock}: Used for fast sequential logic (LFSR, edge detection).
    \item \texttt{slowclock}: Used as a time reference for the game countdown and for flashing LEDs in WAIT\_START mode. Since we don't count time as "seconds" but rather as ticks, we can then adjust the slow clock to adapt the length of the game, thus the difficulty. 
\end{itemize}
An internal \texttt{global\_tick} counter (0 to 63) acts as a pre-divider to pace the appearance of moles and their duration on the screen. This approach is more efficient than individual per-mole counters, since it does use fewer timers, and thus precious logic cells. 
\newline
\newline
\emph{Prescaler Memory Optimization:} Since the \texttt{fastclock} oscillates very fast, if we used the clock directly to control their visibility, moles would appear then disappear instantly. If each of the 9 moles counted to several hundred cycles individually to stay visible for a second, we would need a massive 10-bit integer ($2^{10}$) for each mole ($9 \times 10 = 90$ Flip-Flops), which would immediately overflow our 160 LE constraint. Instead, the \texttt{global\_tick} acts as a centralized frequency divider (prescaler). By routing the \texttt{fastclock} through a single 6-bit counter (0 to 63), we generate the condition \texttt{global\_tick = 0} to act as a shared, synchronized ``low-frequency virtual third clock''. This allows each mole's state machine to use a single bit logic vector (\texttt{mole\_duration}) to track its appearance time relative to the prescaler, while having the clock run quickly enough for every other process to work properly. 

Here is how the timer updates are implemented in VHDL. We use a \texttt{slowclock\_prev} signal to detect the rising edge of the slow clock synchronously within the \texttt{fastclock} process:
\begin{lstlisting}[language=VHDL]
-- Gestion du Timer de jeu total et penalites
if (slowclock = '1' and slowclock_prev = '0') or trigger_miss = '1' then
    if game_duration_timer > 0 then
        game_duration_timer <= game_duration_timer - 1;
    end if;
end if;

-- Transition a la fin du temps
if game_duration_timer = 0 then
    game_state <= WAIT_START;
end if;

-- Et dans un processus separe (timer_proc)
-- Global Tick Prescaler (0 a 63)
if global_tick = 63 then
    global_tick <= 0;
else
    global_tick <= global_tick + 1;
end if;
\end{lstlisting}

\subsection{Game Logic and Hit Detection}
During the \texttt{PLAYING} state, the \texttt{moles\_fsm\_proc} process continuously loops over the 9 buttons to evaluate user inputs against the \texttt{mole\_active} tracking array:
\begin{itemize}
    \item \textbf{Non-Deterministic Spawning}: Initially, our spawning logic simply populated two moles immediately when available. Because moles had identical lifespans (exactly 2 global ticks), this inadvertently created an infinite, highly predictable \texttt{2-1-2-1-2} visual loop pattern on the grid. We solved this by using the lowest bit of the LFSR to introduce a 50\% chance of spawning a second mole immediately or delaying it:
\begin{lstlisting}[language=VHDL]
if global_tick = 0 and (active_count = 0 or (active_count < 2 and lfsr(0) = '1')) then
    -- Spawn new mole logic execution
end if;
\end{lstlisting}
    \item \textbf{Hit}: Successfully hitting an active mole sets \texttt{trigger\_hit <= '1'}, \texttt{timer\_proc} enabling \texttt{score\_high} signal for 8 fastclock ticks (ensuring external CD4026B chips correctly register the pulse).
    \item \textbf{Miss/Error}: Hitting an empty spot flags a \texttt{wrong\_click}, which activates \texttt{trigger\_miss <= '1'}. This instantly decrements the global game timer by 1 tick and lights up the \texttt{penalty\_led} for visualizing that we have indeed pressed the wrong spot for the mole, or that we were too slow.
\end{itemize}

\section{Hardware Validation}
Unlike traditional workflows relying on functional VHDL simulations or testbenches, the validation of this project was performed entirely live on real hardware. We iteratively compiled, then flashed and tested the code on the CPLD

Since we could afford to build a prototype right away, we used this advantage to iterate a lot more quickly than editing our test bench and then watching our program fail miserably in real-life conditions. We are aware that this approach is not the best one, since building a prototype before designing the logic circuit can become very expensive pretty quickly, and that in many cases it is not possible to do, however the project was small enough to let us build the circuit in parallel of programming the CPLD

\section{Hardware Implementation and optimizations}
Keeping the compiled program inside the 160 logic elements boundaries was quite challenging, especially since our first approach was using a big procedural singular block without state machines, all controlled by fastclock. We realized pretty quickly that this approach was neither very clean nor maintainable.

We chose to use this CPLD in combination with CD4026B chips to display the score outside of the logic design. This prevents overwhelming the CPLD with unnecessary combinational routing data (e.g., seven-segment pattern logic), simplifying the VHDL and integrating the CPLD natively as a discrete logical "brain" in a bigger electronic circuit. 
We used a tool called KiCAD to design the schematic of the circuit, using real component references, and a schematic of the CPLD development board. Pierre tried at one point to create a real PCB for the project, but because we took too long to finish the project, and missed the deadline before which we were able to order PCBs, he stopped at the beginning of the design. This however could easily be achieved with the tools we have at the moment.

The schematic shows clearly debouncing circuits on each of the buttons, to ensure that every click is only registered once, and does not need to be filtered digitally. On the final design those circuits are barely visible, and it's for a simple reason : We used  0804 and 0402 SMD components (resistors and capacitors) to build the debouncing circuits, to take less space first, but also because those components are a lot less expensive to get in bulk. The circuit itself is not particularly complex, and we used the datasheets of every component to design the circuit, as well as the traditional 10Kohm resistors for pullup/pulldown signals.

\section{Conclusion}
The "Whack-a-mole" project allowed us to apply synchronization concepts (signals) for asynchronous events (buttons) and real-time management on a CPLD. The use of an LFSR added an interesting layer of complexity to randomness management, and the management of a finite state machine revealed being trickier than expected. User inputs and de-bouncing circuits are fascinating, and developing both an electrical circuit, and the code to control it was quite fun. 

We experienced some unexpected results, most notably the one that the RLE view of the circuit does, in fact, not implement a state-machine. This fact was mentioned earlier in the report, however we were expecting a state machine at one point in the logic circuit, but no. Quartus compiled the project without state machines. See the figure \ref{fig:RLEView} just below. Despite having done our code as a state machine, it seems the most optimal code for what we want does not involve a state machine at all.
