\section{Introduction}
This project was carried out as part of the Digital Electronics course (ELEN0040). The objective is to design and implement a classic "Whack-a-mole" game on a CPLD (Complex Programmable Logic Device).

The game consists of hitting "moles" represented by LEDs that light up randomly on a grid. The player must press the button corresponding to the lit LED to score points within a limited time. This implementation utilizes fundamental digital logic concepts such as Finite State Machines (FSM), clock synchronization, and pseudo-random number generation via a Linear Feedback Shift Register (LFSR). 

The project was constrained by the hardware limitations of the CPLD, specifically a maximum of 160 Logic Elements (LE), which heavily influenced our design choices and optimizations.

The report is structured as follows: Section 2 details the system specifications and hardware interface. Section 3 explains the logic architecture, including the FSM and synchronization mechanisms. Section 4 covers hardware validation, while Section 5 focuses on the physical implementation and optimizations. Finally, Section 6 concludes the report with a summary of challenges and results.

\section{System Specifications}

\subsection{Game Interface}
The user interface consists of:
\begin{itemize}
    \item \textbf{9 LEDs}: Arranged in a grid, representing the mole locations.
    \item \textbf{9 Buttons}: Each associated with an LED.
    \item \textbf{1 Start Button}: To initiate a new game session.
    \item \textbf{Score Signals}: \texttt{penalty\_led} to visually indicate incorrect presses, as well as two 7-segment displays to display the player's score at any point in the game. 
\end{itemize}

This "hardware-offloading" approach was both the easiest to implement and the most expandable (ex : counting up to 999 could be achieved by simply cascading more controllers).

\section{Logic Architecture}

\subsection{Architecture Overview and Signal Synchronization}
The logic of the \texttt{Whackamole} entity is designed around a modular architecture consisting of four independent VHDL processes. Instead of a purely sequential execution, the system relies on a "process-trigger" paradigm where specialized blocks communicate via internal signals (flags). This approach ensures that timing-critical tasks (like LFSR generation) are isolated from game-level logic.

The four main processes are:
\begin{itemize}
    \item \textbf{lfsr\_proc}: Continuously generates pseudo-random sequences at every \texttt{fastclock} cycle.
    \item \textbf{timer\_proc}: Generates the \texttt{global\_tick} prescaler and handles the pulse-stretching (else signals would be too short to be noticed) for output signals (\texttt{score\_high}, \texttt{penalty\_led}).
    \item \textbf{game\_fsm\_proc}: Manages the global game states (\texttt{WAIT\_START}, \texttt{PLAYING}) and the overall countdown.
    \item \textbf{moles\_fsm\_proc}: The core logic that tracks the 9 moles, handles spawning probabilities, and detects user hits.
\end{itemize}

This modular approach allows each process to operate independently, facilitating modular debugging and timing management. While this architecture requires more internal signals (using additional Logic Elements), it provides very good maintainability and ease-of-understanding. 

\subsection{Internal Signals and Constants}
To facilitate communication between the independent processes, several internal signals were defined. These act as the "nervous system" of the CPLD, carrying triggers and status information across the architecture:

\begin{itemize}
    \item \textbf{game\_state}: An enumerated type (\texttt{WAIT\_START}, \texttt{PLAYING}) that controls the global behavior of the system.
    \item \textbf{mole\_active}: A 9-bit vector where each bit indicates if a mole is currently "up" and visible to the player.
    \item \textbf{mole\_duration}: A 9-bit vector used as a secondary state bit for each mole. It allows moles to persist for a controlled number of \texttt{global\_tick} cycles (ensuring they don't disappear too fast).
    \item \textbf{global\_tick}: A 6-bit counter (0 to 63) acting as a centralized frequency divider (prescaler) to synchronize the spawning and lifespan of moles. This mechanism is crucial for resource optimization, as discussed in Section 3.5.
    \item \textbf{trigger\_hit} / \textbf{trigger\_miss}: Single-cycle pulses used to communicate events from the \texttt{moles\_fsm\_proc} to the \texttt{timer\_proc} and the external displays.
    \item \textbf{score\_timer} / \textbf{error\_timer}: Counters used to "stretch" short clock pulses into longer signals that are detectable by the external hardware (CD4026B).
\end{itemize}

\subsection{Finite State Machine (FSM)}
The core control logic of the game is handled by the \texttt{game\_fsm\_proc} process through a finite state machine with two primary states:
\begin{itemize}
    \item \textbf{WAIT\_START (IDLE)}: The default state upon power-up and game over. In this state, all LEDs blink synchronously with the \texttt{slowclock}. This tells the player the machine is ready to interact with him.  The system transitions to \texttt{PLAYING} when the \texttt{startButton} is pressed.
    \item \textbf{PLAYING}: The active game state lasting 30 timer ticks. When the \texttt{game\_duration\_timer} reaches zero, the system returns back to \texttt{WAIT\_START}.
\end{itemize}

As shown in Figure \ref{fig:game_fsm}, the system remains in the \texttt{WAIT\_START} state until the player initiates the game.


The initialization and transition of these states are managed within the main FSM process:
\begin{lstlisting}[language=VHDL]
type game_state_type is (WAIT_START, PLAYING);
signal game_state : game_state_type := WAIT_START;
-- ... inside game_fsm_proc
case game_state is
    when WAIT_START =>
        score_reset <= '0';
        game_duration_timer <= 30; -- Main timer reset
        if startButton = '0' and startButton_prev = '1' then
            game_state <= PLAYING;
            score_reset <= '1'; -- Reset pulse to display
        end if;

    when PLAYING =>
        score_reset <= '0';
        
        -- Handle total game timer and penalties
        if (slowclock = '1' and slowclock_prev = '0') or trigger_miss = '1' then
            if game_duration_timer > 0 then
                game_duration_timer <= game_duration_timer - 1;
            end if;
        end if;

        -- Transition at end of time
        if game_duration_timer = 0 then
            game_state <= WAIT_START;
        end if;
end case;
\end{lstlisting}

\emph{Note:} Interestingly, the RTL analysis shows that Quartus does not synthesize explicit FSM blocks for this code. Instead, it optimizes the state transitions into a series of standard logic gates. We assume that this behavior is common when the state machine is relatively simple (2 states). For proof, we tried putting a dummy third state and Quartus compiled a FSM. 

\subsection{Pseudo-Random Generation (LFSR)}
To ensure the unpredictability of mole appearances, we implemented a pseudo-random input generator. Instead of relying on complex external noise sources, we used a Linear-Feedback Shift Register (LFSR). Specifically, we implemented a 5-bit LFSR with the polynomial $x^5 + x^3 + 1$. This component generates a sequence of numbers that appear random to our human eye despite being deterministic.
\begin{lstlisting}[language=VHDL]
lfsr <= lfsr(3 downto 0) & (lfsr(4) xor lfsr(2));
\end{lstlisting}

At each \texttt{fastclock} cycle, the register evolves. When the system decides to spawn a new mole, the current value of the LFSR (truncated to 4 bits) is converted to an index between 0 and 8. The sequence begins with [10000] to ensure the pattern does not get stuck in an all-zero state. Since the \texttt{fastclock} runs continuously while the user is in the \texttt{WAIT\_START} state, the starting value for each game session is effectively randomized based on the duration of the wait. It might be important to note that this is not RNG (Random Number Generation). We are not generating random numbers, but a random input to use for processes that need one. 

\subsection{Time Management and Synchronization}
The system uses two clocks passed through the ports:
\begin{itemize}
    \item \texttt{fastclock}: Used for fast sequential logic (LFSR, edge detection).
    \item \texttt{slowclock}: Used as a time reference for the game countdown and for flashing LEDs in WAIT\_START mode. Since we don't count time as "seconds" but rather as ticks, we can then adjust the slowclock to adapt the length of the game, thus the difficulty. 
\end{itemize}
An internal \texttt{global\_tick} counter (0 to 63) acts as a pre-divider to pace the appearance of moles and their duration on the screen. This approach is more efficient than individual per-mole counters, significantly reducing the number of logic cells required.

\emph{Prescaler Memory Optimization:} Given the 160 LE constraint of our CPLD, minimizing flip-flop usage was critical. The \texttt{fastclock} oscillates at approximately 200-300\,Hz. If each of the 9 moles required an individual 10-bit counter to remain visible for roughly one second, we would need 90 flip-flops just for mole timing. Instead, our centralized \texttt{global\_tick} uses a single 6-bit counter to generate a shared synchronization signal. Each mole then only requires a single-bit status flag (\texttt{mole\_duration}), reducing the total requirement to just $6 + 9 = 15$ flip-flops.This is a memory saving of over 83\%.

Here is how the timer updates are implemented in VHDL. We use a \texttt{slowclock\_prev} signal to detect the rising edge of the slow clock synchronously within the \texttt{fastclock} process:
\begin{lstlisting}[language=VHDL]
-- Handle game timer and penalties
if (slowclock = '1' and slowclock_prev = '0') or trigger_miss = '1' then
    if game_duration_timer > 0 then
        game_duration_timer <= game_duration_timer - 1;
    end if;
end if;

-- Transition at the end of the timer
if game_duration_timer = 0 then
    game_state <= WAIT_START;
end if;

-- Prescaler in a separate process (timer_proc)
-- Global Tick Prescaler (0 to 63)
if global_tick = 63 then
    global_tick <= 0;
else
    global_tick <= global_tick + 1;
end if;
\end{lstlisting}
\subsection{Mole Logic and Hit Detection}
The \texttt{moles\_fsm\_proc} is the core of the game logic. It manages 9 independent virtual entities in parallel, evaluating the state of the grid at every clock cycle.

\subsubsection{Non-Deterministic Spawning}
Initially, our spawning logic simply populated two moles immediately when available. Because moles had identical lifespans (exactly 2 global ticks), this created an infinite, highly predictable \texttt{2-1-2-1-2} visual loop pattern on the grid. To solve this, we introduced an added 50\% probability check using the lowest bit of the LFSR:
\begin{lstlisting}[language=VHDL]
if global_tick = 0 and (active_count = 0 or (active_count < 2 and lfsr(0) = '1')) then
    -- Spawn new mole logic execution
end if;
\end{lstlisting}
This ensures that a second mole only appears if \texttt{lfsr(0)} is '1', breaking the predictability of the mole spawning process

\subsubsection{Asynchronous Input Synchronization}
Since buttons are pressed by a human, they are asynchronous to the system clock. We use edge detection (comparing \texttt{button} with \texttt{button\_prev}) to ensure a single press only triggers one event:
\begin{itemize}
    \item \textbf{Hit}: Successfully hitting an active mole sets \texttt{trigger\_hit <= '1'}. This activates the \texttt{score\_high} signal for a duration controlled by \texttt{score\_timer}, ensuring the external CD4026B counters register the pulse correctly.
    \item \textbf{Miss/Error}: Hitting an empty spot (where \texttt{mole\_active} is '0') sets the \texttt{wrong\_click} flag. This triggers a penalty: the global game timer is decremented, and the \texttt{penalty\_led} lights up for visual feedback.
\end{itemize}

\section{Hardware Implementation and optimizations}
Keeping the compiled program inside the 160 logic elements boundaries was quite challenging, especially without some of the optimizations we used. 

We chose to use this CPLD in combination with CD4026B chips to display the score outside of the logic design. This prevents overwhelming the CPLD with unnecessary combinational routing data (e.g., seven-segment pattern logic), simplifying the VHDL and integrating the CPLD natively as a discrete logical "brain" in a bigger electronic circuit. 
We used KiCAD to design the system's electronic schematic, incorporating real component references and a model of the CPLD development board.

The schematic shows clearly debouncing circuits on each of the buttons, to ensure that every click is only registered once, and does not need to be filtered digitally. On the final design those circuits are barely visible, and it's for a simple reason: we used 0804 and 0402 SMD components (resistors and capacitors) to build the debouncing circuits, to take less space first, but also because those components are a lot less expensive to get in bulk. Those debouncing circuits are critical for logic purposes, since the CPLD allows for no margin of error when it comes to asynchronous inputs like buttons. Since the behaviour of tactile buttons can become quite unexpected, leading to single presses to be registered as multiple presses(switch bounce), the use of a filter to ensure one press is not registered as multiple presses causing penalties is very important 
The electrical circuit itself is not particularly complex, and we used the datasheets of the most complex components to design it, as well as the traditional 10\,k$\Omega$ resistors for pull-up/pull-down signals. 

We modularized the design, with one module focused on the scoring display and one module with buttons and LEDs, which is the main interface the player can interact with.

\section{Conclusion}
The "Whack-a-mole" project successfully demonstrated the application of synchronous digital logic to handle asynchronous real-time events. By implementing a modular architecture on a CPLD, we managed to create a fully functional game while staying within the 160 Logic Element constraint.

\subsection*{Summary of Challenges and Solutions}
The primary challenge was balancing the game's complexity with the hardware's limited resources. Our centralized \texttt{global\_tick} prescaler was a critical solution, reducing the required flip-flops by over 80\%. Additionally, implementing a pseudo-random LFSR provided the necessary unpredictability for engaging gameplay. We could have used a different approach like Analog noise detection for example, however keeping the generation inside the CPLD was far easier to do. 

Another interesting observation was the discrepancy between our VHDL state machine structure and the synthesized RTL view. As shown in Figure \ref{fig:RTLView}, Quartus optimized the FSM into a network of logic gates rather than a dedicated state register. This optimization highlights the compiler's efficiency in mapping logical descriptions to specific hardware constraints, even when the human-readable code suggests a more formal FSM structure.

Developing both the digital logic and the physical electronic circuit was a rewarding experience, providing deep insights into the practicalities of hardware design, from debouncing circuits to modular prototyping.
